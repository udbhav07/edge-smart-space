# User test: findings for a developer

**Date:** 2026-10-08, about 21:40–22:20 local (IST), during peak tariff until 22:00.
**Tested by:** someone acting as an occupant and operator, using only what the README and `--help` describe. No source was read and nothing was run "as a developer".
**Build:** branch `fix/live-run-defects`, head `677436a`. Windows 11, Git Bash and PowerShell, real mosquitto broker, Ollama serving `qwen2.5:7b`, CUDA available. All services started with `python start.py`, speech included. Layer 1 was the simulator.

Each finding gives the steps a user takes, what they expected, what happened, and what would count as fixed. Severity is from the occupant's point of view:

- **High:** the system does the wrong thing to the room or the calendar, or tells the occupant something false.
- **Medium:** a feature fails or misleads, but nothing is harmed.
- **Low:** polish.

IDs are stable; refer to them in commit messages.

## High

### U-01: A calendar follow-up changed the room temperature

**Steps**
```
python -m tools.say "put a meeting with Ravi on Thursday at 3"
python -m tools.say "move it to 4"
```
**Expected:** the meeting moves to 16:00, or the system asks what "it" is.
**Actual:** `heard as: environment, 4 C, cooler`, then "4 degrees is outside the safe range of 18 to 30, so the closest I can do is 18 degrees; it is heading there". `tools.blackboard_view` later showed `GOAL 18.0 C from preference`, and the loop drove the room toward 18 °C.
**Why it matters:** an ordinary follow-up about a meeting made the room colder. Short-term context exists for the assistant, but the first classification of an utterance does not use it.
**Fixed when:** a follow-up immediately after a calendar exchange is read against that exchange, and an ambiguous bare number never becomes a setpoint without being about temperature.

### U-02: "Cancel the meeting" creates a meeting

**Steps**
```
python -m tools.say "put a meeting with Ravi on Thursday at 3"
python -m tools.say "cancel the meeting with Ravi"
```
**Expected:** the entry is removed, or "I can't cancel entries yet".
**Actual:** "Added Cancel Meeting with Ravi at 15:00 on Thursday 8 October." `state/calendar.json` now holds both "Meeting with Ravi" and "Cancel Meeting with Ravi" at 15:00. No clash was mentioned.
**Fixed when:** there is a way to remove or move an entry by voice (FR-58 already says entries are removable), the system never creates an entry whose subject is a request to cancel, and a double booking at the same time is mentioned.

### U-03: Told "Done" when nothing will happen

**Steps**
```
python -m tools.inject ac dead
# wait about 12 min until the mode is DEGRADED_ACTUATOR
python -m tools.say "make it cooler please"
```
**Expected:** "The air conditioner isn't responding and is on hold; I can't cool the room until someone checks it."
**Actual:** "Done. The room is now set to 20 degrees."
The same happens in DEGRADED_SENSOR (stuck sensor): every reply says "Done. The room is now set to …" and never mentions that control is running on an estimate.
**Fixed when:** a temperature reply reflects the mode. In DEGRADED_ACTUATOR or SAFE_HOLD it says plainly that the request cannot take effect; in DEGRADED_SENSOR it says the sensor is out and the room is controlled on an estimate.

### U-04: Peak tariff makes the reply untrue

**Steps** (between 18:00 and 22:00 local)
```
python -m tools.say "make it 22 degrees"
python -m tools.blackboard_view
```
**Expected:** "Set to 22 °C. It's peak-tariff time, so the room is held at 23 until 22:00."
**Actual:** "Done. The room is now set to 22 degrees." The viewer shows `GOAL 23.0 C` after a later "make it 23", while the startup log says `tariff is peak; tracking 25.00 C`, meaning +1 °C is applied. The viewer shows neither the tariff band nor the temperature actually being held.
**Fixed when:** replies and the viewer show both the asked-for setpoint and the one actually held, with the reason.

### U-05: Enrolment accepts a recording with no voice in it

**Steps** (nobody speaking near the laptop microphone)
```
printf '\n\n\n' | python -m tools.enroll ravi --name Ravi --record 3 --seconds 2
```
**Expected:** "No speech heard in recording 1; try again."
**Actual:** "voiceprint for ravi now holds 3 utterance(s) / the voice can be recognised". The voiceprint is room noise.
**Why it matters:** a noise print can match random sounds as Ravi and give out Ravi's memory. Recognition grants no permissions, but it does select whose facts are read out.
**Fixed when:** enrolment refuses a recording without enough speech (the voice-activity detector the pipeline already uses would do) and says how much speech it heard; 2 s is also too short to be accepted.

### U-06: The room cannot talk about itself

**Steps** (the third one during a stuck-sensor fault)
```
python -m tools.say "what's the temperature in here"
python -m tools.say "is everything working ok"
python -m tools.say --as ravi "what do you know about me"
```
**Expected:** the current temperature and setpoint; "the temperature sensor is faulty and I'm running on an estimate"; what is remembered about Ravi.
**Actual:**
- "I passed that on, but nothing changed the target temperature."
- nothing at all ("nothing actionable was heard")
- nothing at all

The Fault Diagnosis messages are good ("The temperature sensor seems to have stopped sending data, so the system is using its model…"), but they appear only in the service log. An occupant has no way to hear or see them (FR-28 asks for a notification).
**Fixed when:** an occupant can ask the temperature, the system's health and what it remembers about them, and is told about a fault when it happens.

### U-07: Remember, forget and recall are unreliable

**Steps** (with `ravi` enrolled)
```
python -m tools.say --as ravi "please remember that I am vegetarian"        # dropped
python -m tools.say --as ravi "remember I like meetings after 10am"         # kept
python -m tools.say --as ravi "I prefer the room at 23 degrees, remember that"  # kept as a fact
python -m tools.say --as ravi "what do you know about me"                   # dropped
python -m tools.say --as ravi "forget that I am vegetarian"                 # dropped
python -m tools.say --as ravi "remember that I like tea"                    # dropped
```
**Expected:** all of them work.
**Actual:** 2 of 6 worked. "Forget" never reached the system in any phrasing tried. The unit tests pass only because they script the model; with the real model the first classification step drops these as "nothing actionable".
**Fixed when:** at least these phrasings work against the served model, measured the way E6 measures tool selection, with forget and recall included.

### U-08: Misread comfort, and questions treated as commands

**Steps**
```
python -m tools.say "it's a bit stuffy in here"
python -m tools.say "why is it so warm"
```
**Expected:** "stuffy" means cooler or fresher; a "why" question gets an answer, not an action.
**Actual:** "stuffy" was heard as warmer and the room was set to 25 °C. "Why is it so warm" lowered the setpoint to 21 °C.
**Fixed when:** comfort words are read correctly (stuffy, muggy and close mean cooler) and a question is answered rather than acted on, or the system says what it is about to change.

## Medium

### U-09: First answer takes 85 seconds
The first `tools.say "make it 22 degrees"` after `start.py` took 1 min 25 s. After that each request took 9–11 s. Nothing told the user to wait, and `start.py` reported "ok inference server" while the model was still cold.
**Fixed when:** startup warms the model, or the first reply says "one moment, I'm waking up"; `start.py --check` says whether the model is loaded.

### U-10: tools.say crashes on non-English text (Windows)
`python -m tools.say "हवा ठंडी करो"` gives `UnicodeEncodeError: 'charmap' codec can't encode…` at `print(f"you: …")`. With `PYTHONIOENCODING=utf-8` the system understood Hindi fine ("cooler", set to 22). Emoji will crash the same way.
**Fixed when:** the tools never crash on the console encoding.

### U-11: tools.inject reports injections that did not happen
```
python -m tools.inject temp01 stuck 27      # typo: warns, then "injected", exit 0
python -m tools.inject pir_01 drift 0.1     # "injected DRIFT on pir_01"
python -m tools.inject ac stuck 20          # "injected STUCK_AT on ac"
```
The simulator log shows all three refused ("unknown subject", "BinarySensor cannot inject DRIFT", "an actuator cannot be STUCK_AT"). The user is told they worked, and the typo leaves a retained message on `space/inject/temp01` indefinitely. `--list` already knows the supported faults per subject.
**Fixed when:** the CLI refuses an unknown subject or unsupported fault before publishing, with a non-zero exit, and reports what the device did.

### U-12: Starting twice runs two rooms
With the system already running, `python start.py --only simulator` started a second simulator without complaint. Two plants then publish `temp_01` on the same topics, and the estimator sees readings from two rooms.
**Fixed when:** `start.py` notices the services are already present (on the broker or by process) and refuses or warns.

### U-13: Bring-up passes a stuck sensor
With `temp_01` stuck at 27.0, `python -m tools.bringup --seconds 30` printed `temp_01 6 5s 5.0s 0.00s 27.000 0.0000 ok`. Six identical readings with zero spread is exactly a sensor that reports but doesn't measure. The outdoor row is misaligned (`--s --s`), and hum_01 shows `p95 jit 5.00s`, which looks like a dropout counted as jitter.
**Fixed when:** zero spread on a continuous sensor gets a warning verdict.

### U-14: The broken sensor disappears, and so does the explanation
During the dropout the viewer's SENSORS list showed hum_01, pir_01 and pwr_01, but **no temp_01 at all**. The faulted sensor should be at the top, marked silent. The diagnosis text was written to the log, and the viewer listed `space/diagnosis/+` as "silent" because it started after the message was sent.
**Fixed when:** a faulted or silent sensor stays in the view with its state, and the latest diagnosis per active fault is visible to someone who opens the viewer later.

### U-15: Hand edits are silently ignored
I replaced `state/profiles/ravi.md` with:
```
Ravi notes

facts:
* likes tea
- allergic to dust

## facts
- lowercase heading fact

## Facts
- proper fact
```
`tools.profiles show ravi` listed only "proper fact". The others ("likes tea", "allergic to dust", "lowercase heading fact") and the name were dropped without a warning, and the display name fell back to `ravi`. The file says "Edit it freely".
**Fixed when:** headings are case-insensitive, `*` bullets and `facts:` are accepted or reported, and `tools.profiles show` warns about lines it could not read.

### U-16: The "heard as" line shows the wrong direction
`make it 40` → `heard as: environment, 40 C, cooler`; `make it 24 degrees` (room target 18) → `24 C, cooler`. Every named number seems to be labelled "cooler".
**Fixed when:** the direction matches the request, or is not shown when a number is given.

### U-17: The calendar accepts the past and promises reminders
- "put a meeting with Ravi on Thursday at 3", said on Thursday at 21:44, was booked for **15:00 today**, already six hours past, with no comment.
- "schedule dentist yesterday at 5pm" was booked for yesterday without comment.
- "remind me to call mom in 10 minutes" → "Added Call Mom at 21:54". Nothing reminded me at 21:54; there is no reminder mechanism.

**Fixed when:** a time already in the past is questioned (and a weekday that is today, after its time, means next week), and "remind me" either reminds or says that it only adds an entry.

### U-18: Reset makes a still-broken unit look fixed
With the unit still dead, `python -m tools.reset --reason "checked it"` → mode `NORMAL: operator reset; no faults active`. Nothing warned that the detector re-tests and will likely raise the fault again in about 10 minutes. The command's only output is "watch space/system/mode".
**Fixed when:** reset reports the resulting mode and says that faults are re-tested from scratch.

### U-19: Internal error text is spoken
After `python -m tools.profiles delete ravi --yes`, `tools.say --as ravi "remember I like meetings after 10am"` replied: "profile_memory could not do it: nobody is enrolled as 'ravi'".
**Fixed when:** provider failures are turned into occupant language ("I don't have a profile for you any more").

### U-20: Guests share one conversation
`tools.profiles list` showed `guest … 10 recent` after a handful of unrelated requests. Every unrecognised speaker gets the same history: one visitor's calendar talk is put into the prompt for the next person.
**Fixed when:** guest context is short-lived and not shared across clearly separate conversations, or this is a stated, accepted choice.

### U-21: The meter shows the unit off; nothing else agrees
With `ac dead`, the viewer showed `ac COOL … ack UNKNOWN` beside `pwr_01 16.000 W`. The meter makes it obvious the compressor is not running, but in the simulator the acknowledgement stays UNKNOWN and D5 still needed about 12 minutes.
**Fixed when:** the simulator path acknowledges from the meter as the hardware bridge does, and the viewer does not show COOL beside a standby draw without comment.

### U-22: The viewer's stream does not work in a pipe
`python -m tools.blackboard_view --stream | grep fault` printed nothing for 40 s; the output seems block-buffered when not a terminal. The stream also prints Python reprs for some messages (`source=<GoalSource.PREFERENCE: 'preference'>`) and dicts for others.
**Fixed when:** the stream flushes per line and prints one consistent, readable format.

### U-23: The README's watch commands do not work on Windows
`mosquitto_sub` is installed (`C:\Program Files\mosquitto`) but is not on PATH, and the README's single-quoted topics (`'space/#'`) are wrong for cmd and PowerShell. `python -m tools.blackboard_view`, which works everywhere, is not mentioned in the README.
**Fixed when:** the README leads with `tools.blackboard_view` and gives Windows forms for the mosquitto commands.

### U-24: No way in without recordings
- `tools.profiles` has no "create"; only `tools.enroll` makes a profile, and it needs audio.
- The README does not say how to make a 16 kHz mono WAV.
- `python -m tools.enroll ravi --record 1` with no interactive stdin crashes with an `EOFError` traceback.

**Fixed when:** a profile can be created by name alone (voice added later), the README explains recordings, and `--record` fails politely without a terminal.

### U-25: Greetings get silence
`python -m tools.say "hello"` → "nothing actionable was heard". A person greeting the room hears nothing.
**Fixed when:** small talk gets a short reply.

## What worked, and must keep working

- **Startup:** `start.py --check`, then `start.py`, brought every service up, speech on CUDA included.
- **The safety gate:** 5 °C → 18, 40 °C → 30, both explained honestly; rate limiting explained ("changes a couple of degrees at a time").
- **Bookings:** confirm and decline both work, the mock is labelled in every sentence, and missing details are asked for.
- **Dropout:** detected in seconds, DEGRADED_SENSOR, cooling continued on the model, a good diagnosis written, NORMAL again about 2 min after clearing.
- **Stuck sensor:** detected; the estimator restarted from 27.08 °C, not the frozen 27.00 (the re-anchoring is visible).
- **Killing the reasoning process:** `start.py` restarted it, and a request a few seconds later was still answered.
- **Dead air conditioner:** detected (slowly) and DEGRADED_ACTUATOR entered.
- **Hindi:** understood correctly once the console encoding was not in the way.
- **Recording and replay** work.
- **`tools.demo`** tells the whole story in about a second.
- **Profiles:** `tools.profiles list`, `show` and `delete` work on the files; `delete` asks first.
